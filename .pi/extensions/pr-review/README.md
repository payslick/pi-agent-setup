# PR review extension

Recovered PR review workflow.

## Commands

- `/pr-create [pr-number|branch] [--base=main] [--no-sync] [--no-checks] [--no-push] [--no-ci-watch] [--screenshots <file>] [--skip-screenshots] [--ready]` — create or update a GitHub PR from the current branch (new PRs are drafts unless `--ready`), following the installed `pr-metadata` skill for title/body policy plus the label, stale-docs, uploaded-screenshot, preflight, CI-watch, and self-review workflow.
- `/pr-update [pr-number] [--no-checks] [--no-push] [--no-metadata]` — sync an existing PR branch with its base, resolve migration/code conflicts, fix stale docs references, run checks, push, refresh PR metadata when needed, and start CI watch.
- `/pr-review [pr-number] [--no-agents] [--lanes=a,b] [--open-visual]` — fetch a GitHub PR with `gh`, run lane reviewers, and render a report.
- `/pr-review-local [base-ref] [--no-agents] [--lanes=a,b] [--open-visual]` — review the local diff against a base ref (default `origin/main`).
- `/pr-review-process [pr-number] [--include-resolved]` — verify the current branch PR, read review comments and related code, plan rule-backed fixes for all-caps `NEVER`/`ALWAYS` instructions, and group remaining comments for follow-up agents.
- `/pr-review-rerender [results-json] [--open-visual]` — re-render cached review results from `tmp/{pi-session}/reports/`.
- `/pr-review-visual [--no-open]` — open/show the latest HTML report.
- `/pr-review-status` — show the latest run status and report paths.
- `/pr-review-demo` — render a synthetic grouped report.
- `/pr-review-update` — no-op compatibility command for the recovered local implementation.

## Runtime layout

The extension loads readable source modules directly; it does not decode or execute a generated payload. `impl.js` is a static public facade and `runtime/extension.js` registers commands. `review.js` orchestrates initial/local reviews; `review-agents.js`, `findings.js`, `issues.js`, `artifacts.js`, `review-ci.js`, `review-reports.js`, and `rendering.js` separate agent execution, parsing, consolidation, artifacts, CI, reports, and terminal rendering. `github.js`, `lanes.js`, `posting.js`, `summary.js`, and `visual.js` are readable plain-JavaScript leaf modules. Editable lane system-prompt instructions live in `prompts/lanes/<lane>.md`, with shared rules in `prompts/shared.md`; these files are read for every review run, so changing lane behavior does not require editing extension JavaScript. `pr-create.js` and `pr-update.js` own PR lifecycle commands with shared helpers in `pr-lifecycle-shared.js`, while `post-review-analysis.js` owns reusable post-review analysis helpers. The focused `/pr-review-process` workflow remains in `process.ts` with its analysis and policy helpers in adjacent source files.

## Behavior

The workflow excludes files under `drizzle/` from review data, lane routing, and findings, then routes the remaining diff through focused lanes (`correctness`, `pr-metadata`, `relevance`, `security-api`, `tests`, `docs`, `architecture`, `code-quality`, `dedupe`, `data`, plus conditional lanes). Before preparing comments, it reads all existing PR comments, including resolved review threads, suppresses equivalent findings, and creates reply drafts only when a finding adds substantial new context to an existing issue. The `dedupe` lane uses `project_index_search` to find similar or identical code and suggest concrete reuse/refactor paths. During `/pr-create`, related issue and PR context is gathered from changed PRDs, the branch name, and explicit command input. Stale-doc repair processes each affected document independently, accepts only unique exact replacements, and uses a seven-minute per-document agent timeout (`PI_PR_DOCS_FIX_AGENT_TIMEOUT_MS` overrides it) before preflight; both stages run before all worktree changes are committed and pushed. The command then fetches the remote, rebases onto the existing PR's branch base, resolves conflicts, and pushes the rebased branch; passing a different `--base` requires confirmation before that new base is used. Screenshot planning considers only changed `.tsx` files and requires meaningful, intentional visual changes; test helpers, import-only edits, non-rendered components, and output-preserving refactors do not require captures. Only confirmed visual changes trigger a dev-server check. If the server is offline, the command repeatedly asks whether to retry or explicitly skip screenshots before continuing. A requested post-create self-review invokes the `/pr-review` extension directly, never posts comments automatically, and displays the normal review action prompt after generating the report. GitHub comments prefer exact `suggestion` blocks, then typed code examples, then concise prose; prose is limited to 400 characters and two sentences, and multi-line suggestions include GitHub range coordinates. Shared PR data is written once under `tmp/{pi-session}/shared/`; each lane writes its assembled `system-prompt.md`, dynamic `prompt.md`, packet data, stdout/stderr, and parsed findings under `tmp/{pi-session}/{lane}/`. Reports are written under `tmp/{pi-session}/reports/` as Markdown, HTML, cached results JSON, and a dry-run GitHub review payload when applicable. Review, CI-analysis, repair, post-review analysis, and policy worktree agents are launched through Herdr in separate unfocused tabs and must return structured results. Lane agents load `prompt.md` through a generated short command instead of pasting the full diff through the terminal. Their tabs set subagent and sound-suppression environment flags, so completing agents do not play sounds. Successful synchronous review tabs close after their final response; startup failures and completion timeouts also close their tabs so orphaned work cannot continue after the report, while other failed review tabs remain available for inspection and long-running policy worktree tabs remain open. Lane turns receive at least 45 minutes. After that baseline, a lane remains alive until ten minutes after its latest persisted session message, so active work near the baseline is not cut off; `PI_REVIEW_AGENT_TIMEOUT_MS` and `PI_REVIEW_AGENT_INACTIVITY_TIMEOUT_MS` override those limits. Every review lane can use `read-many-files-lines` for bounded read-only investigation without a fixed call limit, while the shared prompt directs agents to prefer the supplied lane context and avoid broad, repeated, or overlapping reads. Delegated children inherit the reviewed worktree as their project root. Optional direct tools include `read`, `read-many-files-lines`, Tavily web tools, project-index tools, and `edit`. Bash is disabled except for `ci-analysis`, where an agent-specific guard permits only direct read-only `gh pr checks`, `gh run list`, and `gh run view` calls; the guard also blocks edits outside the lane directory and shared directory. CI is watched by a low-effort `gh`-only agent; if checks fail, a smarter `ci-analysis` lane reads the CI artifacts/logs and returns findings. While review agents run, the footer shows an aggregate live summary with completed, active, and failed counts plus elapsed time. An untruncated, width-aware widget updates every second, packs up to four aligned lane entries per line, and shows each lane's lifecycle phase (`waiting`, `preparing`, `queued`, `starting`, `submitting`, `working`, `finalizing`, `done`, `error`, or `skipped`), elapsed time with the working-session message count in parentheses (for example `05:32(16)`), and confirmed finding count. A `timeout MM:SS` warning appears only during the final five minutes. Findings explicitly confirmed through `report_pr_review_finding` are written to the lane's append-only `partial-findings.jsonl` and deduplicated for the live `found` count while a lane works. On completion, the parent appends the authoritative final findings and freezes the displayed count from the final assistant JSON so a stale artifact poll cannot overwrite it. If a lane fails or times out, valid deduplicated entries already recorded in its partial artifact are recovered into the report, labeled as partial, and excluded from GitHub comment drafts; other lane failures remain isolated so report generation continues. From a completed report, Vim normal-mode `Space`, the issue number, then `Enter` opens a focused Herdr tab running Hunk on the reviewed PR diff, adds the selected finding as an inline agent note, and focuses its code line.

`/pr-review-process` runs a post-review pass over PR comments, confirms the current branch matches the PR branch, reads code around line-specific comments, and renders a workflow table. Every comment authored by the authenticated GitHub user is a mandatory command unless its trimmed body starts with `AI-IGNORE`; after completing a command, the workflow replaces that original comment with a short action-taken summary. Comments from other authors receive normal replies. All-caps `NEVER`/`ALWAYS` comments become rule-workflow tasks: create a design/ESLint rule, prove it fails on the commented file, fix the underlying issue until the rule passes, run it on all changed files, reply to the comment with the rule and occurrence count, then scan the whole codebase and spin off broad unrelated cleanup in a separate worktree/agent when needed. Other comments are grouped by issue type so one high-effort agent per group can fix, ask for clarification, or explain why the comment is not relevant. Correctness and security comments follow a strict regression-first protocol: write a focused test, state the exact expected failure before running it, confirm it fails for that reason, and only then change production code; if the issue cannot be demonstrated, production code remains unchanged and the comment is reported as blocked or not actionable. After fixes and validation, the generated follow-up prompt presents a pre-publish summary, explains how to inspect tracked and untracked changes with `hunk diff` from the PR worktree, and asks once for approval to commit and push before it mutates GitHub comments or resolves completed threads. It verifies the remote PR head before posting and refetches comments afterward so unverified publication work is never reported as complete.

The main-window renderer keeps normal issue rows in the three-column `# | File | Issue` table. Function names are appended inside the File cell as `path :line-range #functionName`. Only `G#` group rows are merged across the File/Issue area so group explanations use the remaining table width. After all lane agents answer, the review pass consolidates repeated underlying issues or similar patterns into these `G#` rows; findings inside a group are sorted by severity. Issue rows include severity color badges: 🔴 critical, 🟡 important, ⚪ mid, 🟢 nit.
