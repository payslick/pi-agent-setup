# PR review extension

Recovered PR review workflow.

## Commands

- `/pr-create [pr-number|branch] [--base=main] [--no-sync] [--no-checks] [--screenshots <file>] [--skip-screenshots]` — create or update a draft GitHub PR from the current branch, following `skills/skills/pr` title/body, label, stale-docs, uploaded-screenshot, preflight, CI-watch, and self-review workflow.
- `/pr-update [pr-number] [--no-checks] [--no-push] [--no-metadata]` — sync an existing PR branch with its base, resolve migration/code conflicts, fix stale docs references, run checks, push, refresh PR metadata when needed, and start CI watch.
- `/pr-review [pr-number] [--no-agents] [--lanes=a,b] [--open-visual]` — fetch a GitHub PR with `gh`, run lane reviewers, and render a report.
- `/pr-review-local [base-ref] [--no-agents] [--lanes=a,b] [--open-visual]` — review the local diff against a base ref (default `origin/main`).
- `/pr-review-process [pr-number] [--include-resolved]` — verify the current branch PR, read review comments and related code, plan rule-backed fixes for all-caps `NEVER`/`ALWAYS` instructions, and group remaining comments for follow-up agents.
- `/pr-review-rerender [results-json] [--open-visual]` — re-render cached review results from `tmp/{pi-session}/reports/`.
- `/pr-review-visual [--no-open]` — open/show the latest HTML report.
- `/pr-review-status` — show the latest run status and report paths.
- `/pr-review-demo` — render a synthetic grouped report.
- `/pr-review-update` — no-op compatibility command for the recovered local implementation.

## Behavior

The workflow routes diffs through focused lanes (`correctness`, `relevance`, `security-api`, `tests`, `docs`, `architecture`, `code-quality`, `dedupe`, `data`, plus conditional lanes). The `dedupe` lane uses `project_index_search` to find similar or identical code and suggest concrete reuse/refactor paths. During `/pr-create`, uncommitted changes are compared with the PR scope: related changes are committed automatically before the branch is pushed, while uncertain or unrelated changes require explicit approval to include or stop the workflow unchanged. The check runs again after preflight tools in case they modify files. Screenshot planning first confirms that the diff has meaningful, intentional visual changes; test helpers, API routes, import-only edits, and output-preserving refactors do not require captures. Only confirmed visual changes trigger a dev-server check. If the server is offline, the command asks whether to retry or skip screenshots before continuing. A requested post-create self-review invokes the `/pr-review` extension directly, never posts comments automatically, and displays the normal review action prompt after generating the report. GitHub comments prefer exact `suggestion` blocks, then typed code examples, then concise prose; prose is limited to 400 characters and two sentences, and multi-line suggestions include GitHub range coordinates. Shared PR data is written once under `tmp/{pi-session}/shared/`; each lane writes prompts, packet data, stdout/stderr, and parsed findings under `tmp/{pi-session}/{lane}/`. Reports are written under `tmp/{pi-session}/reports/` as Markdown, HTML, cached results JSON, and a dry-run GitHub review payload when applicable. Agents are invoked with `pi --print` and must return JSON findings. They can use `read`, `read-many-files-lines`, Tavily web tools, project-index tools, and `edit`; bash is disabled, and an agent-specific guard blocks edits outside its lane directory and the shared directory. CI is watched by a low-effort `gh`-only agent; if checks fail, a smarter `ci-analysis` lane reads the CI artifacts/logs and returns findings. While review agents run, the footer shows compact per-lane status as icon + status only, such as `🐛:running 🔒:done 🗄️:waiting`.

`/pr-review-process` runs a post-review pass over PR comments, confirms the current branch matches the PR branch, reads code around line-specific comments, and renders a workflow table. All-caps `NEVER`/`ALWAYS` comments become rule-workflow tasks: create a design/ESLint rule, prove it fails on the commented file, fix the underlying issue until the rule passes, run it on all changed files, reply to the comment with the rule and occurrence count, then scan the whole codebase and spin off broad unrelated cleanup in a separate worktree/agent when needed. Other comments are grouped by issue type so one high-effort agent per group can fix, ask for clarification, or explain why the comment is not relevant; the generated follow-up prompt asks the user at most once across all groups.

The main-window renderer keeps normal issue rows in the three-column `# | File | Issue` table. Function names are appended inside the File cell as `path :line-range #functionName`. Only `G#` group rows are merged across the File/Issue area so group explanations use the remaining table width. After all lane agents answer, the review pass consolidates repeated underlying issues or similar patterns into these `G#` rows; findings inside a group are sorted by severity. Issue rows include severity color badges: 🔴 critical, 🟡 important, ⚪ mid, 🟢 nit.
