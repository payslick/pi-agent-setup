# PR review extension

Recovered PR review workflow.

## Commands

- `/pr-create [pr-number|branch] [--base=main] [--no-sync] [--no-checks] [--screenshots <file>] [--skip-screenshots]` — create or update a draft GitHub PR from the current branch, following `skills/skills/pr` title/body, label, stale-docs, uploaded-screenshot, preflight, CI-watch, and self-review workflow.
- `/pr-update [pr-number] [--no-checks] [--no-push] [--no-metadata]` — sync an existing PR branch with its base, resolve migration/code conflicts, fix stale docs references, run checks, push, refresh PR metadata when needed, and start CI watch.
- `/pr-review [pr-number] [--no-agents] [--lanes=a,b] [--open-visual]` — fetch a GitHub PR with `gh`, run lane reviewers, and render a report.
- `/pr-review-local [base-ref] [--no-agents] [--lanes=a,b] [--open-visual]` — review the local diff against a base ref (default `origin/main`).
- `/pr-review-process [pr-number] [--include-resolved]` — verify the current branch PR, read review comments and related code, plan rule-backed fixes for all-caps `NEVER`/`ALWAYS` instructions, and group remaining comments for follow-up agents.
- `/pr-review-rerender [results-json] [--open-visual]` — re-render cached review results from `tmp/{pi-session}/reports/`.
- `/pr-review-visual [--no-open]` — open/show the latest HTML report.
- `/pr-review-status` — show the latest run status and report paths.
- `/pr-review-demo` — render a synthetic grouped report.
- `/pr-review-update` — no-op compatibility command for the recovered local implementation.

## Runtime layout

The extension loads readable source modules directly; it does not decode or execute a generated payload. `impl.js` only registers commands and delegates to modules under `runtime/`: `review.js` orchestrates initial/local reviews, with agents, CI, reports, and terminal rendering split into `review-agents.js`, `review-ci.js`, `review-reports.js`, and `rendering.js`; `pr-lifecycle.js` delegates PR creation and updates to `pr-create.js` and `pr-update.js`, backed by `pr-lifecycle-shared.js`; and `after-review.js` owns reusable post-review analysis helpers. The focused `/pr-review-process` workflow remains in `process.ts` with its analysis and policy helpers in adjacent source files.

## Behavior

The workflow routes diffs through focused lanes (`correctness`, `relevance`, `security-api`, `tests`, `docs`, `architecture`, `code-quality`, `dedupe`, `data`, plus conditional lanes). Before preparing comments, it reads all existing PR comments, including resolved review threads, suppresses equivalent findings, and creates reply drafts only when a finding adds substantial new context to an existing issue. The `dedupe` lane uses `project_index_search` to find similar or identical code and suggest concrete reuse/refactor paths. During `/pr-create`, uncommitted changes are compared with the PR scope: related changes are committed automatically before the branch is pushed, while uncertain or unrelated changes require explicit approval to include or stop the workflow unchanged. The check runs again after preflight tools in case they modify files. Screenshot planning first confirms that the diff has meaningful, intentional visual changes; test helpers, API routes, import-only edits, and output-preserving refactors do not require captures. Only confirmed visual changes trigger a dev-server check. If the server is offline, the command asks whether to retry or skip screenshots before continuing. A requested post-create self-review invokes the `/pr-review` extension directly, never posts comments automatically, and displays the normal review action prompt after generating the report. GitHub comments prefer exact `suggestion` blocks, then typed code examples, then concise prose; prose is limited to 400 characters and two sentences, and multi-line suggestions include GitHub range coordinates. Shared PR data is written once under `tmp/{pi-session}/shared/`; each lane writes prompts, packet data, stdout/stderr, and parsed findings under `tmp/{pi-session}/{lane}/`. Reports are written under `tmp/{pi-session}/reports/` as Markdown, HTML, cached results JSON, and a dry-run GitHub review payload when applicable. Review, CI-analysis, repair, post-review analysis, and policy worktree agents are launched through Herdr in separate unfocused tabs and must return structured results. Their tabs set subagent and sound-suppression environment flags, so completing agents do not play sounds. Successful synchronous review tabs close after their final response, failed review tabs remain available for inspection, and long-running policy worktree tabs remain open. They can use `read`, `read-many-files-lines`, Tavily web tools, project-index tools, and `edit`; bash is disabled, and an agent-specific guard blocks edits outside its lane directory and the shared directory. CI is watched by a low-effort `gh`-only agent; if checks fail, a smarter `ci-analysis` lane reads the CI artifacts/logs and returns findings. While review agents run, the footer shows compact per-lane status as icon + status only, such as `🐛:running 🔒:done 🗄️:waiting`.

`/pr-review-process` runs a post-review pass over PR comments, confirms the current branch matches the PR branch, reads code around line-specific comments, and renders a workflow table. Every comment authored by the authenticated GitHub user is a mandatory command unless its trimmed body starts with `AI-IGNORE`; after completing a command, the workflow replaces that original comment with a short action-taken summary. Comments from other authors receive normal replies. All-caps `NEVER`/`ALWAYS` comments become rule-workflow tasks: create a design/ESLint rule, prove it fails on the commented file, fix the underlying issue until the rule passes, run it on all changed files, reply to the comment with the rule and occurrence count, then scan the whole codebase and spin off broad unrelated cleanup in a separate worktree/agent when needed. Other comments are grouped by issue type so one high-effort agent per group can fix, ask for clarification, or explain why the comment is not relevant. Correctness and security comments follow a strict regression-first protocol: write a focused test, state the exact expected failure before running it, confirm it fails for that reason, and only then change production code; if the issue cannot be demonstrated, production code remains unchanged and the comment is reported as blocked or not actionable. After fixes and validation, the generated follow-up prompt presents a pre-publish summary, explains how to inspect tracked and untracked changes with `hunk diff` from the PR worktree, and asks once for approval to commit and push before it mutates GitHub comments or resolves completed threads. It verifies the remote PR head before posting and refetches comments afterward so unverified publication work is never reported as complete.

The main-window renderer keeps normal issue rows in the three-column `# | File | Issue` table. Function names are appended inside the File cell as `path :line-range #functionName`. Only `G#` group rows are merged across the File/Issue area so group explanations use the remaining table width. After all lane agents answer, the review pass consolidates repeated underlying issues or similar patterns into these `G#` rows; findings inside a group are sorted by severity. Issue rows include severity color badges: 🔴 critical, 🟡 important, ⚪ mid, 🟢 nit.
